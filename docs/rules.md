# Learned routing rules

Routing rules express a mailbox preference separately from spam classification. They are useful for messages that should be kept or moved even when they are not spam, such as delivery-status notifications. A matching rule does not change the spam policy or its behavior for messages that proceed to classification. The rule is evaluated first, and the matching message is reported as a rule action without fabricated spam signals.

Rules are local, deterministic, and scoped to configured source folders. Jev is used only while learning, to choose among matcher candidates generated by imapledger. Jev does not generate executable match expressions, folder names, or destinations. Future `clean` runs evaluate the saved matcher locally without calling Jev for that match.

## Learn from one message

A UID is meaningful only within its source folder, so learning requires an explicit folder and destination:

```bash
imapledger rule learn 43627 --folder INBOX.Junk --move INBOX.Trash
```

The source must appear in `spam.folders`. The destination must not be a configured source folder and is checked for existence before the message is fetched. The command fetches only the requested UID from the selected folder, subject to the configured message-size limits. It uses a read-only IMAP session by default.

Jev chooses from a closed set of deterministic candidates built from parsed message headers, such as an exact sender address, list ID, return path, or a subject condition. General domain or subject-only candidates are not automatically accepted. The local acceptance thresholds must also pass. If Jev selects no candidate or the proposal does not meet those safety gates, no rule is saved. Message-provided values are treated as untrusted evidence, never instructions. The message body is excluded from Jev's learning state by default.

Learning displays the candidate, confidence, safety estimate, proposed rule, and explicit move destination. Saving is confirmed with a default-no prompt. The example message is not moved when the rule is saved.

Useful options:

- `--name ID` supplies an optional ID matching lowercase letters, digits, and hyphens, up to 64 characters. Otherwise an ID is generated from the selected matcher.
- `--preview` displays an eligible proposal without saving it.
- `--yes` accepts saving without prompting. It does not move the example message or bypass Jev's safety gates.
- `--apply-current` separately requests moving the referenced UID after the rule has been saved. It opens a writable source session only for this explicit operation. If the move fails, the saved rule is retained and the failure is reported.
- `--preview` and `--apply-current` cannot be combined.
- `--config PATH` selects the configuration file. The rules file is named `rules.toml` beside that file.

For example, `--yes` saves the rule but leaves UID 43627 in place:

```bash
imapledger rule learn 43627 \
  --folder INBOX.Junk \
  --move INBOX.Trash \
  --yes
```

To request the separate current-message move:

```bash
imapledger rule learn 43627 \
  --folder INBOX.Junk \
  --move INBOX.Trash \
  --yes \
  --apply-current
```

## Storage and matching

Rules are stored separately from `config.toml`. For the default configuration, the file is `$XDG_CONFIG_HOME/imapledger/rules.toml`, or `~/.config/imapledger/rules.toml` when `XDG_CONFIG_HOME` is unset. A custom configuration path uses a sibling `rules.toml`. If the rules file is absent, no rules are loaded. Writes are atomic and the resulting file is restricted to the current user.

The versioned TOML format is:

```toml
[rules]
schema = 1

[[rules.rule]]
id = "mailer-daemon-gmx-net"
enabled = true
source_folders = ["INBOX.Junk"]
action = "move"
destination = "INBOX.Trash"
match = { from_address = "mailer-daemon@gmx.net" }
```

Rules support only `keep` and `move` actions. A move destination must exist and must not be any configured source folder. The rule's `source_folders` must be a non-empty subset of `spam.folders`. Learning creates a rule scoped only to the explicitly selected source.

Matcher fields are combined with AND. Supported fields are `from_address`, `from_domain`, `return_path`, `return_path_domain`, `list_id`, `auto_submitted`, `subject`, and `subject_prefix`. Address and domain values are normalized; subject equality and prefix matching are case-insensitive. Rules are checked in file order, and the first enabled rule matching both the current source folder and all matcher fields wins. There are no expressions, regular expressions, OR conditions, or model-generated matchers.

The file is strictly validated, including its schema version, known fields, IDs, actions, matcher fields, and source-folder scope. Invalid rules fail before mailbox processing rather than being silently ignored.

## Apply rules during cleaning

`clean` checks for a matching in-scope rule before spam assessment. A match bypasses the spam classifier for that message and uses the rule's `keep` or `move` action. A non-match continues through the existing spam classifier and policy unchanged. A rule never broadens the configured source-folder list or changes REVIEW behavior for other messages.

Dry-run remains read-only. A matching move is reported as a planned action. With `clean --apply`, the exact UID is moved immediately in the source-scoped session before the next message is processed. Enabled rule move destinations are included in the configured destination allow-list and are preflighted before classification or mutation.

Progress identifies a match with `Rule=<id>`. Per-folder and aggregate summaries count rule matches separately from spam, not-spam, and review outcomes. Rule matches are not assigned a fabricated spam verdict.

## Inspect and manage rules

These local management commands do not connect to IMAP or prompt for a password:

```bash
imapledger rule list
imapledger rule show mailer-daemon-gmx-net
imapledger rule remove mailer-daemon-gmx-net
```

`remove` asks for confirmation with a default of no. Pass `--yes` to remove without the prompt. The CLI currently has no commands for manually adding, editing, enabling, or disabling rules. The interactive TUI provides those operations without using Jev.

## Manage rules in the TUI

Run `imapledger ui` and press `R` to open the Rule Center. Rules are ordered by priority; the first enabled matching rule wins. Create and edit screens use structured matcher fields, source folders, and actions. Manual creation does not invoke Jev or require it to be installed. Sources remain a non-empty subset of `spam.folders`; MOVE destinations must already exist and cannot be configured source folders. Routing rules support KEEP and MOVE only, never DELETE.

Saving a rule writes the local rules file atomically and reloads it into the running session. Save-only does not apply the rule to a message. The separate save-and-apply flow saves first, re-resolves the selected folder and UID, and asks for confirmation before applying only to that exact message. It does not create folders or change `spam.folders`.

The Rule Center can test a rule against a bounded, read-only message window. Testing does not classify or mutate messages. The Action Center, opened with `a`, also links to global outcome policy settings. Those settings apply to future explicit actions, not immediately to stored messages. A global SPAM DELETE policy requires a separate warning and confirmation; it does not delete mail when saved.

## Test a rule read-only

Use `rule test` to inspect a bounded window from the rule's source folders:

```bash
imapledger rule test mailer-daemon-gmx-net --limit 20 --offset 0 --sort newest
```

The default limit is 20 messages per source folder. `--offset` and `--sort` are also applied independently to each source. The command connects read-only, reports matching UIDs with sender and subject, and does not classify, move, delete, or otherwise mutate messages. It resolves the configured credential source once; the default `prompt` source asks for the IMAP password.
